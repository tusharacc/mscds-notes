The Relational Model

Structure of Relational Databases

A relation is essentially a table consisting of:

  • Rows (also called tuples): Represent actual data records
  • Columns (also called attributes): Represent the structure/schema

Example: Instructor Relation

Instructor
+--------+-------------+---------------+--------+
| ID     | Name        | Dept_Name     | Salary |
+--------+-------------+---------------+--------+
| 10101  | Srinivasan  | Comp. Sci.    | 65000  |
| 12121  | Wu          | Finance       | 90000  |
| 15151  | Mozart      | Music         | 40000  |
| 22222  | Einstein    | Physics       | 95000  |
| 32343  | El Said     | History       | 60000  |
| 33456  | Gold        | Physics       | 87000  |
+--------+-------------+---------------+--------+

Mathematical View of Relations

  • Relation schema: R = (A₁, A₂, A₃, ..., Aₙ) - The template/design of the table
  • Relation instance: The actual table with data at a given time
  • Tuple: An element t of relation r, represented by a row
  • Domain: Set of allowed values for each attribute
  • Atomic values: Attributes are indivisible units
  • Null value: Special value indicating unknown data (member of every domain)

Important: Relations are unordered - the order of tuples is irrelevant (set theory principle).

Database Schema vs. Instance

  • Database Schema: Logical structure/design of the database (fixed at design time)
  • Database Instance: Snapshot of data at a given instant (changes as data is added/modified)

Best Practice: Fix your schema during database design and avoid frequent changes. Adding columns later requires populating existing records, which is problematic.

Keys

Super Key

A subset K of attributes R is a super key if K's values are sufficient to uniquely identify each tuple.

Example: In the Instructor table:

  • ID is a super key
  • {ID, Name} is also a super key (any superset of a super key is also a super key)

Candidate Key

A candidate key is a minimal super key - no proper subset is a super key.

Example: ID is a candidate key (minimal), but {ID, Name} is not (not minimal).

Primary Key

One of the candidate keys chosen by the database designer to uniquely identify records.

Example: ID is the primary key for the Instructor table.

Foreign Key

An attribute in one relation that references the primary key of another relation.

Example:

  • Dept_Name in Instructor table references the Department table
  • Referencing relation: Instructor
  • Referenced relation: Department

University Database Schema Example

A realistic database contains multiple related tables:

Core Tables

  1. Instructor (ID, Name, Dept_Name, Salary)
  2. Department (Dept_Name, Building, Budget)
  3. Student (ID, Name, DeptName, TotCredits)
  4. Course (CourseID, Title, DeptName, Credits)
  5. Section (CourseID, SecID, Semester, Year, Building, RoomNumber, TimeSlot_ID)
  6. Teaches (ID, CourseID, SecID, Semester, Year)
  7. Takes (ID, CourseID, SecID, Semester, Year, Grade)
  8. Prereq (CourseID, PrereqID)
  9. Advisor (SID, IID)
  10. Classroom (Building, Room_Number, Capacity)
  11. TimeSlot (TimeSlotID, Day, StartTime, End_Time)

Design Considerations

  • Avoid redundancy (e.g., semester appears in both Takes and Section - redundant)
  • Don't store instructor name in Course table (multiple instructors, multiple semesters)
  • Prerequisites can have multiple rows for one course (one row per prerequisite)

Relational Query Languages

Types of Query Languages

  1. Procedural: Specify WHAT data is needed AND HOW to get it
  2. Non-procedural (Declarative): Specify WHAT data is needed only

Pure Mathematical Languages

  • Relational Algebra (procedural)
  • Tuple Relational Calculus (non-procedural)
  • Domain Relational Calculus (non-procedural)

These languages are:

  • Equivalent in computing power
  • NOT Turing complete (cannot do everything C/Python can do)
  • Designed specifically for database queries

Relational Algebra

A procedural, mathematically-oriented query language based on six basic operations.

Six Basic Operations

#### 1. Select (σ) Selects tuples satisfying a given predicate (condition).

Notation: σₚ(r)

Example: 

σDeptName="Physics"(Instructor)
Returns all instructors in the Physics department.

Comparison Operations Allowed:

  • = (equal)
  • ≠ (not equal)
  • > (greater than)
  • ≥ (greater than or equal)
  • < (less than)
  • ≤ (less than or equal)

Combining Predicates:

  • AND (∧)
  • OR (∨)
  • NOT (¬)

Example: 

σDeptName="Physics" ∧ Salary>90000(Instructor)

Attribute Comparisons: 

σDeptName=Building(Department)

#### 2. Project (Π) Returns a relation with only specified attributes, removing duplicates.

Notation: Π_{A₁, A₂, ..., Aₖ}(r)

Example: 

Π_ID,Name,Salary(Instructor)
Returns only ID, Name, and Salary columns (department name excluded).

Composition Example: 

ΠName(σDept_Name="Physics"(Instructor))
Returns names of all physics department instructors.

#### 3. Cartesian Product (×) Combines information from two relations by creating all possible pairs.

Notation: r × s

Result: For every row in r and every row in s, create a combined row.

Example: 

Instructor × Teaches

Important Notes:

  • Number of result rows = (rows in r) × (rows in s)
  • Attributes with same name get prefixed: Instructor.ID, Teaches.ID
  • Often creates many irrelevant combinations (needs filtering)
  • Computationally expensive - use carefully

#### 4. Join (⋈) Combines Cartesian product with selection - more efficient than separate operations.

Notation: r ⋈_θ s

Mathematical Definition: 

r ⋈θ s = σθ(r × s)

Example: 

Instructor ⋈_Instructor.ID=Teaches.ID Teaches
Returns only rows where instructor ID matches teaches ID.

Why Join is Important:

  • Combines information across tables efficiently
  • Result is typically much smaller than Cartesian product
  • Backend implementations optimize joins beyond simple cross-product filtering

#### 5. Union (∪) Combines two relations into one.

Requirements:

  • Same arity (number of attributes)
  • Compatible attribute domains (same types in same order)

Example: 

ΠCourseID(σ_Semester="Fall" ∧ Year=2017(Section))
∪
ΠCourseID(σ_Semester="Spring" ∧ Year=2018(Section))
Returns courses taught in Fall 2017 OR Spring 2018.

#### 6. Set Difference (−) Returns tuples in first relation but not in second.

Requirements: Same as union (same arity, compatible domains)

Example: 

ΠCourseID(σ_Semester="Fall" ∧ Year=2017(Section))
−
ΠCourseID(σ_Semester="Spring" ∧ Year=2018(Section))
Returns courses taught in Fall 2017 but NOT in Spring 2018.

Additional Operations

#### Set Intersection (∩) Returns tuples present in both relations.

Example: 

ΠCourseID(σ_Semester="Fall" ∧ Year=2017(Section))
∩
ΠCourseID(σ_Semester="Spring" ∧ Year=2018(Section))
Returns courses taught in BOTH Fall 2017 AND Spring 2018.

#### Assignment (←) Stores intermediate results in variables for readability.

Example: 

physics ← σDeptName="Physics"(Instructor)
music ← σDeptName="Music"(Instructor)
physics ∪ music

#### Rename (ρ) Returns result under a new name, enabling use in larger expressions.

Notation: ρ_x(E)

Returns relation E under name x.

Query Equivalence and Optimization

Multiple queries can produce the same result with different efficiency.

Example 1: 

Query 1: σDeptName="Physics" ∧ Salary>90000(Instructor)
Query 2: σDeptName="Physics"(σ_Salary>90000(Instructor))
Both return the same result, but Query 2 may be more efficient if few instructors have salary > 90000.

Example 2: 

Query 1: σDeptName="Physics"(Instructor ⋈ Teaches)
Query 2: σDeptName="Physics"(Instructor) ⋈ Teaches
Query 2 is more efficient - filters before expensive join operation.

Query Optimizer: Database systems automatically choose the most efficient execution plan regardless of how the query is written.

Data Definition Language (DDL)

Language for defining database schema (structure).

SQL DDL Example

CREATE TABLE Instructor (
    ID          CHAR(5),
    Name        VARCHAR(20),
    Dept_Name   VARCHAR(20),
    Salary      NUMERIC(8,2)
);

Data Types:

  • CHAR(n): Fixed-length character string (exactly n characters)
  • VARCHAR(n): Variable-length character string (up to n characters)
  • NUMERIC(p,d): Numeric with p total digits, d after decimal point

DDL Compiler and Data Dictionary

DDL Compiler generates table templates stored in the data dictionary.

Data Dictionary Contains (Metadata):

  • Database schema (table structures, column types)
  • Integrity constraints (e.g., primary keys, salary ≥ 0)
  • Authorization information (who can access what)

Primary Key Constraint: 

CREATE TABLE Instructor (
    ID CHAR(5) PRIMARY KEY,
    ...
);

Data Manipulation Language (DML)

Language for querying and modifying data.

Types of DML

  1. Procedural DML:
  • Specify WHAT data is needed AND HOW to get it
  • User describes exact procedure to retrieve data
  1. Declarative (Non-procedural) DML:
  • Specify WHAT data is needed only
  • Easier to learn and use
  • SQL is a declarative DML

SQL Query Example

SELECT Name
FROM Instructor
WHERE Dept_Name = 'Comp. Sci.';

Components:

  • SELECT: Specifies attributes to retrieve
  • FROM: Specifies table(s)
  • WHERE: Specifies conditions

Input: One or more tables Output: Single table (single column in this example)

SQL is NOT Turing Complete

Cannot do:

  • Arbitrary programs
  • User input
  • Direct screen output
  • Network communication

Solution: Embed SQL in host languages (C, Python, Java)

Language Extensions and APIs

Embedding SQL in Host Languages:

  • Python database modules (e.g., sqlite3, psycopg2)
  • SQL queries passed as strings
  • Results returned to host language

Database APIs:

  • ODBC (Open Database Connectivity)
  • JDBC (Java Database Connectivity)
  • Neutral APIs independent of specific programming languages

Application Programs and Database Access

Databases are used within larger application programs:

  • Web applications (most common)
  • Mobile applications
  • Desktop applications

Typical Flow:

  1. User interacts with application interface
  2. Application generates SQL queries
  3. Database returns results
  4. Application formats and displays results

Database Engine Components

1. Storage Manager

Responsible for storing, retrieving, and updating data efficiently.

Components:

  • Authorization and Integrity Manager: Ensures authorized access only
  • Transaction Manager: Manages transaction execution
  • File Manager: Interacts with OS to manage files on disk
  • Buffer Manager: Manages data movement between disk and main memory

Storage Structures:

  • Data files: Actual table data
  • Data dictionary: Metadata (schema, authorization)
  • Indices: Fast access structures (like textbook index)

Performance Impact: Poor storage management can make simple queries take hours instead of milliseconds.

2. Query Processor

Responsible for executing user queries efficiently.

Components:

#### DDL Interpreter

  • Interprets DDL statements
  • Stores definitions in data dictionary

#### DML Compiler

  • Translates DML queries into query plans
  • Performs query optimization
  • Generates low-level instructions

#### Query Evaluation Engine

  • Executes query plans
  • Returns results

Query Optimization Process:

  1. Parse user query
  2. Translate to relational algebra
  3. Generate multiple possible query plans
  4. Use statistics (table sizes, data distribution) to estimate costs
  5. Select lowest-cost plan
  6. Execute plan

Why Optimization Matters: Can reduce execution time from hours to milliseconds.

3. Transaction Management

A transaction is a collection of operations performing a single logical function.

Example: Money transfer between bank accounts 

-- Both must succeed or both must fail
UPDATE Account SET Balance = Balance - 100 WHERE Account_ID = 'A';
UPDATE Account SET Balance = Balance + 100 WHERE Account_ID = 'B';

Transaction Properties Ensured:

  • Atomicity: All operations complete or none complete (indivisible)
  • Consistency: Database remains in valid state
  • Isolation: Concurrent transactions don't interfere
  • Durability: Committed changes survive failures

Components:

#### Transaction Manager

  • Ensures atomicity and consistency
  • Handles recovery from failures (power, disk, OS crashes)

#### Concurrency Control Manager

  • Allows multiple users to execute transactions simultaneously
  • Prevents conflicts (e.g., two users modifying same account)
  • Uses locking mechanisms
  • Allows parallel read-only transactions

Database Architecture

1. Centralized Architecture

  • Database runs on single machine (possibly powerful server)
  • Multiple cores, shared memory possible
  • Users log into the machine to access database

2. Client-Server Architecture

  • Server: Database engine runs here
  • Clients: Applications connect remotely
  • Most common for web/mobile applications
  • No need to SSH into server

3. Parallel Databases

Speed up execution through parallelism:
  • Shared Memory: Multiple cores, shared memory
  • Shared Disk: Separate memory spaces, shared disk
  • Shared Nothing: Separate machines, data partitioned across them

4. Distributed Databases

  • Geographically distributed database servers
  • Common for large enterprises (multinational corporations)
  • May have schema heterogeneity (different schemas at different locations)
  • Example: Supermarket chain with database at each store

Application Architecture

Two-Tier Architecture

[Client Machine]          [Server Machine]
  Application   <----->   Database System
  • Application on client directly accesses database server

Three-Tier Architecture

[Client Machine]          [Application Server]     [Database Server]
  Web Browser    <----->   Web Application   <---> Database System
  • Client accesses application server (e.g., web server)
  • Application server accesses database
  • Most common for modern web applications

Database Users

1. Naive Users

  • Don't know SQL or query languages
  • Use applications built by programmers
  • Applications execute pre-written queries

2. Application Programmers

  • Write applications containing SQL queries
  • Create compiled application programs
  • Develop user interfaces

3. Sophisticated Users (Analysts)

  • Know SQL or other query languages
  • Don't necessarily write full applications
  • Perform data analysis and generate reports
  • Understand business domain and translate to queries
  • Use query tools for analysis

4. Database Administrators (DBAs)

Responsibilities:

  • Schema definition: Design table structures
  • Storage structure and access methods: Decide physical organization
  • Schema modification: Modify structure when needed
  • Authorization: Grant user access rights
  • Routine maintenance: Monitor disk space, backups, etc.

Importance: DBAs are key assets to organizations, often well-compensated, not just doing mundane tasks.

History of Database Systems

1950s-1960s: Early Data Processing

  • Storage: Magnetic tapes (sequential access, slow)
  • Input: Punch cards
  • Impact: Programmers were more careful due to difficulty of making changes

1960s-1970s: Hard Disks Emerge

  • Storage: Hard disks enabled random access
  • Models: Network and hierarchical data models popular

1970s: Relational Model Revolution

  • Ted Codd defined the relational model (ACM Turing Award winner)
  • Prototypes:
  • IBM's System R
  • UC Berkeley's Ingres (Michael Stonebraker)
  • Commercial: Oracle released first commercial relational DBMS
  • Still captures ~50% of database market today

1980s: Relational Systems Mature

  • Research on query optimization, transaction processing, logging
  • Development of parallel and distributed databases
  • Object-oriented databases emerge (niche market)

1990s: Decision Support and Web

  • Data warehousing: Multi-terabyte repositories
  • Data mining: Decision support applications
  • OLAP: Online Analytical Processing
  • Web commerce: Database-backed web applications

2000s: Big Data Era

  • Big Data Systems: Google BigTable, Yahoo PNUTS, Amazon systems
  • NoSQL: Designed for horizontal scalability across machines
  • Criticism of SQL: Limited to single-machine scalability
  • Use Case: Very large-scale applications (Facebook, Google)
  • MapReduce: Data analysis on distributed systems

2010s: SQL Reloaded

  • SQL front-ends: For MapReduce systems
  • Massively parallel databases: Using SQL
  • Main-memory databases: Entire database fits in RAM
  • Main memory became cheaper
  • Eliminates disk I/O bottleneck
  • Hundreds of times faster than disk-based systems
  • Reality: Both SQL and NoSQL coexist, serving different needs

Current State

  • Relational databases: Still dominant for medium-scale applications
  • NoSQL: Best for very large-scale, horizontally-scalable applications
  • Main-memory databases: For applications fitting in RAM
  • Trade-offs: Relational provides flexibility and general queries; NoSQL provides scalability

Week 2: Introduction to SQL

Week 2: Introduction to SQL

Overview

This week introduces SQL (Structured Query Language), the practical query language used across relational database systems. We cover SQL history and standardization, data definition language (DDL) for creating database schemas, basic query structure with SELECT-FROM-WHERE, and data manipulation operations. The content emphasizes practical SQL usage with SQLite demonstrations and covers essential concepts like joins, string operations, and aggregate functions.

Key Concepts

  • SQL vs Relational Algebra: SQL is a practical, standardized language for database operations, while relational algebra is a mathematical foundation
  • SQL Standardization: ANSI/ISO standards (SQL-86, SQL-92, SQL-99, SQL:2003, SQL:2023) ensure portability across database vendors
  • Data Definition Language (DDL): Commands for creating and modifying database structure (CREATE, ALTER, DROP)
  • Data Manipulation Language (DML): Commands for querying and modifying data (SELECT, INSERT, UPDATE, DELETE)
  • Primary Key: Unique identifier for records in a table
  • Foreign Key: Reference to a primary key in another table, maintaining referential integrity
  • Natural Join: Joins tables by matching all common attributes automatically

SQL Components

Parts of SQL

  1. Data Manipulation Language (DML): Insert, delete, modify records
  2. Data Definition Language (DDL): Define schemas, integrity constraints, views
  3. Transaction Control: Begin/end transactions with atomicity guarantees
  4. Embedded SQL: Integrate SQL within general-purpose languages (C, Python, Java)
  5. Authorization: Control user access to tables and columns

Domain Types (Data Types)

String Types

  • CHAR(n): Fixed-length string of exactly n characters (padded with spaces)
  • VARCHAR(n): Variable-length string up to n characters (more space-efficient)

Numeric Types

  • INT: Machine-dependent integer (typically 64-bit)
  • SMALLINT: Smaller integer (typically 2 bytes)
  • NUMERIC(p, d): Fixed precision decimal with p total digits, d after decimal point
  • Example: NUMERIC(3,1) can store 44.5 but not 444.5 or 0.32
  • REAL, DOUBLE PRECISION: Floating-point numbers
  • FLOAT(n): Floating-point with precision n

Other Types

  • DATE: Calendar date
  • TIME: Time of day

Data Definition Language (DDL)

Creating Tables

CREATE TABLE instructor (
    id CHAR(5),
    name VARCHAR(20) NOT NULL,
    dept_name VARCHAR(20),
    salary NUMERIC(8,2),
    PRIMARY KEY (id),
    FOREIGN KEY (dept_name) REFERENCES department
);

Integrity Constraints

  • PRIMARY KEY: Unique, non-null identifier
  • FOREIGN KEY: References another table's primary key
  • NOT NULL: Attribute cannot have null values

Table Modification

-- Add a column
ALTER TABLE instructor ADD COLUMN office VARCHAR(10);
-- Remove a column
ALTER TABLE instructor DROP COLUMN office;
-- Delete all records
DELETE FROM instructor;
-- Remove entire table
DROP TABLE instructor;

Warning: When adding columns to existing tables, all current records get NULL values for the new column.

Basic SQL Query Structure

SELECT-FROM-WHERE Pattern

SELECT A1, A2, ..., An
FROM r1, r2, ..., rm
WHERE P;
  • SELECT clause: Specifies attributes to retrieve (corresponds to projection in relational algebra)
  • FROM clause: Lists relations to query (performs Cartesian product)
  • WHERE clause: Specifies conditions/predicates (corresponds to selection in relational algebra)

Important: SQL's SELECT corresponds to relational algebra's project (π), not select (σ)

Examples

-- Simple selection
SELECT name FROM instructor;
-- With condition
SELECT name
FROM instructor
WHERE dept_name = 'Comp. Sci.' AND salary > 70000;
-- Select all columns
SELECT * FROM instructor;
-- Rename output column
SELECT salary/12 AS monthly_salary FROM instructor;

Distinct and Duplicate Handling

Handling Duplicates

-- SQL allows duplicates by default (unlike relational algebra)
SELECT dept_name FROM instructor;  -- May show duplicates
-- Remove duplicates
SELECT DISTINCT dept_name FROM instructor;
-- Force showing all (including duplicates)
SELECT ALL dept_name FROM instructor;

String Operations

Pattern Matching with LIKE

  • % matches any substring (like * in Unix)
  • _ matches exactly one character (like ? in Unix)
-- Names starting with 'j'
SELECT name FROM instructor WHERE name LIKE 'j%';
-- Names containing 'dir'
SELECT name FROM instructor WHERE name LIKE '%dir%';
-- Exactly 3 characters
SELECT name FROM instructor WHERE name LIKE '_';
-- At least 3 characters
SELECT name FROM instructor WHERE name LIKE '_%';
-- Escape literal %
SELECT name WHERE name LIKE 'ab\%cd%' ESCAPE '\';

Note: Patterns are case-sensitive in most SQL implementations (though SQLite may differ)

String Functions

  • || : String concatenation
  • UPPER(), LOWER(): Case conversion
  • LENGTH(): String length
  • SUBSTRING(): Extract substring

Ordering Results

-- Ascending order (default)
ORDER BY name;
-- Descending order
ORDER BY salary DESC;
-- Multiple attributes
ORDER BY dept_name, name;  -- First by dept, then by name within each dept

Comparison and Range Operators

Comparison Operators

  • = : Equal (single equals, not ==)
  • <> : Not equal (NOT !=)
  • <, <=, >, >= : Standard comparisons

BETWEEN Operator

-- Shorthand for range
WHERE salary BETWEEN 90000 AND 100000;
-- Equivalent to
WHERE salary >= 90000 AND salary <= 100000;

Tuple Comparison

-- Compare multiple values at once
WHERE (instructor.id, dept_name) = (teaches.id, 'Biology');
-- Equivalent to
WHERE instructor.id = teaches.id AND dept_name = 'Biology';

Joins

Cartesian Product (Cross Join)

SELECT * FROM instructor, teaches;

Generates every possible combination of records from both tables.

Natural Join (Implicit)

-- Using WHERE clause
SELECT name, course_id
FROM instructor, teaches
WHERE instructor.id = teaches.id;

Self-Join with Renaming

-- Find instructors with salary > some CS instructor
SELECT T.name
FROM instructor AS T, instructor AS S
WHERE T.salary > S.salary AND S.dept_name = 'Comp. Sci.';
-- Note: AS keyword is optional
FROM instructor T, instructor S

Self-Join Example: Employee-Supervisor

-- Find supervisor of Bob
SELECT supervisor
FROM emp_super
WHERE person = 'Bob';
-- Find supervisor of supervisor of Bob
SELECT S2.supervisor
FROM empsuper S1, empsuper S2
WHERE S1.person = 'Bob' AND S1.supervisor = S2.person;

Set Operations

UNION, INTERSECT, EXCEPT

-- Courses in Fall 2017 OR Spring 2018
(SELECT course_id FROM section WHERE semester = 'Fall' AND year = 2017)
UNION
(SELECT course_id FROM section WHERE semester = 'Spring' AND year = 2018);
-- Courses in BOTH semesters (intersection)
(SELECT course_id FROM section WHERE semester = 'Fall' AND year = 2017)
INTERSECT
(SELECT course_id FROM section WHERE semester = 'Spring' AND year = 2018);
-- Courses in Fall 2017 but NOT Spring 2018
(SELECT course_id FROM section WHERE semester = 'Fall' AND year = 2017)
EXCEPT
(SELECT course_id FROM section WHERE semester = 'Spring' AND year = 2018);

Note: Set operations automatically eliminate duplicates. Use UNION ALL, INTERSECT ALL, EXCEPT ALL to retain duplicates.

Null Values

Handling NULL

-- Check for null
SELECT name FROM instructor WHERE salary IS NULL;
-- Check for non-null
SELECT name FROM instructor WHERE salary IS NOT NULL;

NULL in Arithmetic and Comparisons

  • Any arithmetic operation with NULL returns NULL: 5 + NULL = NULL
  • Any comparison with NULL returns UNKNOWN (not NULL): 5 < NULL = UNKNOWN
  • WHERE clause treats UNKNOWN as FALSE

Three-Valued Logic

| AND | TRUE | FALSE | UNKNOWN | |-----|------|-------|---------| | TRUE | TRUE | FALSE | UNKNOWN | | FALSE | FALSE | FALSE | FALSE | | UNKNOWN | UNKNOWN | FALSE | UNKNOWN |

| OR | TRUE | FALSE | UNKNOWN | |----|------|-------|---------| | TRUE | TRUE | TRUE | TRUE | | FALSE | TRUE | FALSE | UNKNOWN | | UNKNOWN | TRUE | UNKNOWN | UNKNOWN |

Aggregate Functions

Functions

  • AVG(): Average value
  • MIN(): Minimum value
  • MAX(): Maximum value
  • SUM(): Sum of values
  • COUNT(): Count of rows

Examples

-- Average salary in CS department
SELECT AVG(salary)
FROM instructor
WHERE dept_name = 'Comp. Sci.';
-- Number of instructors
SELECT COUNT(*) FROM instructor;
-- Number of distinct salaries
SELECT COUNT(DISTINCT salary) FROM instructor;

GROUP BY

-- Average salary per department
SELECT deptname, AVG(salary) AS avgsalary
FROM instructor
GROUP BY dept_name;

Rule: Attributes in SELECT must either:

  1. Appear in GROUP BY clause, OR
  2. Be inside an aggregate function
-- WRONG: id not in GROUP BY
SELECT deptname, id, AVG(salary) FROM instructor GROUP BY deptname;
-- CORRECT
SELECT deptname, AVG(salary) FROM instructor GROUP BY deptname;

HAVING Clause

Filters groups (like WHERE filters rows):

-- Departments with average salary > 42000
SELECT deptname, AVG(salary) AS avgsalary
FROM instructor
GROUP BY dept_name
HAVING AVG(salary) > 42000;

WHERE vs HAVING:

  • WHERE: Filters individual records before grouping
  • HAVING: Filters groups after aggregation

Data Manipulation

INSERT

-- Single record
INSERT INTO instructor VALUES ('10211', 'Smith', 'Biology', 66000);
-- Specify columns (different order)
INSERT INTO course (title, courseid, credits, deptname)
VALUES ('Database Systems', 'CS-437', 4, 'Comp. Sci.');
-- Insert with NULL
INSERT INTO student VALUES ('3003', 'Green', 'Finance', NULL);
-- Insert from query
INSERT INTO instructor
SELECT id, name, dept_name, 18000
FROM student
WHERE deptname = 'Music' AND totalcredits > 144;

DELETE

-- Delete all records
DELETE FROM student;
-- Delete with condition
DELETE FROM instructor WHERE dept_name = 'Finance';
-- Delete with subquery
DELETE FROM instructor
WHERE dept_name IN (
    SELECT dept_name FROM department WHERE building = 'Watson'
);
-- Delete based on aggregate
DELETE FROM instructor
WHERE salary < (SELECT AVG(salary) FROM instructor);

Important: SQL evaluates the entire SELECT before deleting, so average is computed on original data.

UPDATE

-- Give 5% raise to all
UPDATE instructor SET salary = salary * 1.05;
-- Conditional update
UPDATE instructor
SET salary = salary * 1.05
WHERE salary < 70000;
-- Update with subquery
UPDATE instructor
SET salary = salary * 1.05
WHERE salary < (SELECT AVG(salary) FROM instructor);
-- Conditional update with CASE
UPDATE instructor
SET salary = CASE
    WHEN salary <= 100000 THEN salary * 1.05
    ELSE salary * 1.03
END;

SQLite Differences from Standard SQL

  1. Types are optional: SQLite infers types (defaults to VARCHAR for text)
  2. Foreign keys disabled by default: Use PRAGMA foreign_keys = ON; to enable
  3. Case-insensitive LIKE: Unlike most SQL implementations
  4. Dot commands: Special commands starting with . (like .tables, .schema)

Important Notes and Best Practices

Design Principles

  1. Avoid NULL when possible: NULL values complicate queries and can cause unexpected behavior
  2. Use appropriate data types: Choose CHAR for fixed-length, VARCHAR for variable-length
  3. Define integrity constraints: Use PRIMARY KEY and FOREIGN KEY to maintain data consistency
  4. Fixed table schemas: Design tables upfront; rarely ALTER after deployment
  5. One table per entity type: Don't create separate tables for each student/course (violates normalization)

Common Mistakes

  1. Using == instead of =: SQL uses single equals for comparison
  2. Using != instead of <>: Standard SQL uses <> for not-equal
  3. Forgetting DISTINCT: SQL allows duplicates by default
  4. Mixing up WHERE and HAVING: WHERE for rows, HAVING for groups
  5. Wrong attribute names in GROUP BY: Attributes in SELECT must be in GROUP BY or aggregated

Performance Tips

  1. Use indexes for frequently queried columns (covered in later chapters)
  2. Aggregate in SQL rather than application code (more efficient)
  3. Let SQL optimize joins: Database engines optimize Cartesian products automatically

Nested Subqueries

Subqueries allow embedding one query within another, enabling powerful multi-step data retrieval.

Subquery Locations

  1. FROM clause: Subquery result becomes a temporary table
  2. WHERE clause: Subquery result used in conditions
  3. SELECT clause: Must return single value (scalar subquery)

Set Membership: IN and NOT IN

-- Courses in Fall 2017 AND Spring 2018 (intersection)
SELECT DISTINCT course_id
FROM section
WHERE semester = 'Fall' AND year = 2017
  AND course_id IN (
      SELECT course_id
      FROM section
      WHERE semester = 'Spring' AND year = 2018
  );
-- Courses in Fall 2017 but NOT in Spring 2018 (difference)
SELECT DISTINCT course_id
FROM section
WHERE semester = 'Fall' AND year = 2017
  AND course_id NOT IN (
      SELECT course_id
      FROM section
      WHERE semester = 'Spring' AND year = 2018
  );
-- Simple usage
SELECT name
FROM instructor
WHERE name NOT IN ('Mozart', 'Einstein');

Set Comparison: SOME and ALL

SOME (or ANY): True if condition holds for at least one value

-- Find instructors with salary > SOME instructor in Biology
-- (i.e., greater than the minimum Biology salary)
SELECT name
FROM instructor
WHERE salary > SOME (
    SELECT salary
    FROM instructor
    WHERE dept_name = 'Biology'
);

Semantics of SOME:

  • 5 < SOME (0, 5, 6) → TRUE (5 < 6)
  • 5 < SOME (0, 5) → FALSE (not less than any)
  • 5 = SOME (0, 5) → TRUE (equals 5)
  • 5 <> SOME (4, 6) → TRUE (5 ≠ 4)
  • = SOME is equivalent to IN
  • <> SOME is NOT equivalent to NOT IN

ALL: True if condition holds for all values

-- Find instructors with salary > ALL instructors in Biology
-- (i.e., greater than the maximum Biology salary)
SELECT name
FROM instructor
WHERE salary > ALL (
    SELECT salary
    FROM instructor
    WHERE dept_name = 'Biology'
);

Semantics of ALL:

  • 5 < ALL (6, 10) → TRUE (less than both)
  • 5 < ALL (4, 5, 6) → FALSE (not less than 4 or 5)
  • 5 = ALL (5, 5) → Could be TRUE if all are 5
  • 5 <> ALL (4, 6) → TRUE (not equal to any)
  • <> ALL is equivalent to NOT IN

EXISTS and NOT EXISTS

EXISTS: Returns TRUE if subquery returns any results (non-empty set)

-- Courses offered in both Fall 2017 and Spring 2018
SELECT course_id
FROM section AS S
WHERE semester = 'Fall' AND year = 2017
  AND EXISTS (
      SELECT *
      FROM section AS T
      WHERE semester = 'Spring' AND year = 2018
        AND S.courseid = T.courseid
  );

NOT EXISTS: Returns TRUE if subquery returns no results (empty set)

-- Students who have taken ALL courses offered by Biology department
SELECT S.id, S.name
FROM student AS S
WHERE NOT EXISTS (
    -- Courses in Biology that student S has NOT taken
    (SELECT courseid FROM course WHERE deptname = 'Biology')
    EXCEPT
    (SELECT T.course_id FROM takes AS T WHERE S.id = T.id)
);

Key Insight: X - Y = ∅ is equivalent to X ⊆ Y (X is subset of Y)

UNIQUE

Tests whether subquery has duplicate tuples (returns TRUE if no duplicates)

-- Find courses offered at most once in 2017
SELECT T.course_id
FROM course AS T
WHERE UNIQUE (
    SELECT R.course_id
    FROM section AS R
    WHERE T.courseid = R.courseid AND year = 2017
);

Subqueries in FROM Clause

-- Departments with average salary > 42000 (without HAVING)
SELECT deptname, avgsalary
FROM (
    SELECT deptname, AVG(salary) AS avgsalary
    FROM instructor
    GROUP BY dept_name
) AS dept_avg
WHERE avg_salary > 42000;
-- Rename entire result table
SELECT dept_name, average
FROM (
    SELECT dept_name, AVG(salary)
    FROM instructor
    GROUP BY dept_name
) AS deptavg(deptname, average)
WHERE average > 42000;

WITH Clause

Defines temporary named result sets for cleaner queries:

-- Find departments with maximum budget
WITH max_budget(value) AS (
    SELECT MAX(budget)
    FROM department
)
SELECT dept_name
FROM department, max_budget
WHERE department.budget = max_budget.value;
-- Complex query with multiple WITH clauses
WITH depttotal(deptname, value) AS (
    SELECT dept_name, SUM(salary)
    FROM instructor
    GROUP BY dept_name
),
depttotalavg(value) AS (
    SELECT AVG(value)
    FROM dept_total
)
SELECT dept_name
FROM depttotal, depttotal_avg
WHERE depttotal.value > depttotal_avg.value;

Scalar Subqueries

Must return exactly one value (single row, single column):

-- List departments with number of instructors
SELECT dept_name, (
    SELECT COUNT(*)
    FROM instructor
    WHERE department.deptname = instructor.deptname
) AS num_instructors
FROM department;

Error if subquery returns multiple values!

Join Operations

Join Types and Conditions

SQL supports combining join type with join condition:

Join Types (how to handle non-matching tuples):

  • INNER JOIN: Discard non-matching tuples (default)
  • LEFT OUTER JOIN: Preserve tuples from left relation
  • RIGHT OUTER JOIN: Preserve tuples from right relation
  • FULL OUTER JOIN: Preserve tuples from both relations

Join Conditions (how to match tuples):

  • NATURAL: Match all common attributes
  • USING (A1, A2, ...): Match specified attributes
  • ON : Match using custom condition

Natural Join

Automatically matches all attributes with the same name:

-- List student names with courses they've taken
SELECT name, course_id
FROM student NATURAL JOIN takes;

Without natural join (equivalent): 

SELECT name, course_id
FROM student, takes
WHERE student.id = takes.id;

Caution: Natural join matches ALL common attributes, which may cause issues if unrelated attributes share names (e.g., name in student vs name in course).

Inner Join with ON

Explicitly specify join condition:

SELECT *
FROM student JOIN takes ON student.id = takes.id;

Key Difference from Natural Join: Common attributes appear twice in result (e.g., student.id and takes.id both present)

Outer Joins

Preserve information from relations even when no match exists.

#### Example Tables

course: | courseid | title | deptname | credits | |-----------|-------|-----------|---------| | BIO-301 | Genetics | Biology | 4 | | CS-190 | Game Design | Comp. Sci. | 4 | | CS-315 | Robotics | Comp. Sci. | 3 |

prereq: | courseid | prereqid | |-----------|-----------| | BIO-301 | BIO-101 | | CS-190 | CS-101 | | CS-347 | CS-101 |

Note: CS-315 has no prerequisites; CS-347 exists in prereq but not in course table.

#### LEFT OUTER JOIN

Preserve all tuples from left relation:

SELECT *
FROM course NATURAL LEFT OUTER JOIN prereq;

Result: | courseid | title | deptname | credits | prereq_id | |-----------|-------|-----------|---------|-----------| | BIO-301 | Genetics | Biology | 4 | BIO-101 | | CS-190 | Game Design | Comp. Sci. | 4 | CS-101 | | CS-315 | Robotics | Comp. Sci. | 3 | NULL |

Symbol: ⟕ (left side preserved)

#### RIGHT OUTER JOIN

Preserve all tuples from right relation:

SELECT *
FROM course NATURAL RIGHT OUTER JOIN prereq;

Result: | courseid | title | deptname | credits | prereq_id | |-----------|-------|-----------|---------|-----------| | BIO-301 | Genetics | Biology | 4 | BIO-101 | | CS-190 | Game Design | Comp. Sci. | 4 | CS-101 | | CS-347 | NULL | NULL | NULL | CS-101 |

Symbol: ⟖ (right side preserved)

#### FULL OUTER JOIN

Preserve tuples from both relations:

SELECT *
FROM course NATURAL FULL OUTER JOIN prereq;

Result: | courseid | title | deptname | credits | prereq_id | |-----------|-------|-----------|---------|-----------| | BIO-301 | Genetics | Biology | 4 | BIO-101 | | CS-190 | Game Design | Comp. Sci. | 4 | CS-101 | | CS-315 | Robotics | Comp. Sci. | 3 | NULL | | CS-347 | NULL | NULL | NULL | CS-101 |

Symbol: ⟗ (both sides preserved)

USING Clause

Specify which attributes to use for natural join:

-- Join only on course_id (not all common attributes)
SELECT *
FROM course FULL OUTER JOIN prereq USING (course_id);

Advantage: Prevents unintended matches on attributes like name that may have different meanings.

Difference from ON: With USING, common attribute appears once in output; with ON, it appears twice.

Join Examples Summary

-- Natural inner join (default)
course NATURAL JOIN prereq
-- Natural left outer join
course NATURAL LEFT OUTER JOIN prereq
-- Using specific columns
course FULL OUTER JOIN prereq USING (course_id)
-- Explicit condition
course LEFT OUTER JOIN prereq ON course.courseid = prereq.courseid

Views

Views are virtual tables defined by queries, providing:

  1. Data abstraction: Hide complexity
  2. Security: Restrict access to specific data
  3. Simplification: Reuse complex queries

Creating Views

-- View of instructors without salary information
CREATE VIEW faculty AS
SELECT id, name, dept_name
FROM instructor;
-- View with aggregation
CREATE VIEW dept_stats AS
SELECT deptname, COUNT(*) AS numinstructors
FROM instructor
GROUP BY dept_name;

Using Views

-- Query view like a table
SELECT name FROM faculty WHERE dept_name = 'Biology';
-- Views can reference other views
CREATE VIEW physics_faculty AS
SELECT * FROM faculty WHERE dept_name = 'Physics';

Materialized Views

  • Logical views: Recomputed each query (standard)
  • Materialized views: Stored physically, updated when base tables change
  • Faster queries but requires maintenance
  • Not in standard SQL but supported by many vendors

Updating Views

Simple views (single table, no aggregates) are updatable:

-- Allowed
INSERT INTO faculty VALUES ('30128', 'Green', 'Music');
-- Translates to
INSERT INTO instructor VALUES ('30128', 'Green', 'Music', NULL);

Complex views (joins, aggregates) generally not updatable:

-- Most systems reject this
INSERT INTO dept_stats VALUES ('Psychology', 10);

Reason: Ambiguous how to update base tables.

Transactions

A transaction is a sequence of queries/updates treated as a single unit:

-- Transfer $50 from A to B
BEGIN TRANSACTION;
UPDATE account SET balance = balance - 50 WHERE account_number = 'A-101';
UPDATE account SET balance = balance + 50 WHERE account_number = 'A-201';
COMMIT;

ACID Properties

  • Atomicity: All operations succeed or all fail (no partial execution)
  • Consistency: Database remains in valid state
  • Isolation: Concurrent transactions don't interfere
  • Durability: Committed changes survive crashes

Transaction Commands

  • BEGIN TRANSACTION: Start transaction
  • COMMIT: Finalize changes
  • ROLLBACK: Undo all changes since BEGIN
BEGIN TRANSACTION;
DELETE FROM instructor WHERE dept_name = 'Finance';
-- Oops, mistake!
ROLLBACK;  -- Undo deletion

Integrity Constraints

Ensure database consistency by preventing invalid data.

Constraint Types

  1. NOT NULL: Attribute cannot be null
  2. PRIMARY KEY: Unique, non-null identifier
  3. FOREIGN KEY: References primary key in another table
  4. UNIQUE: No duplicate values (but allows multiple NULLs)
  5. CHECK: Custom condition

Examples

CREATE TABLE instructor (
    id CHAR(5) PRIMARY KEY,
    name VARCHAR(20) NOT NULL,
    dept_name VARCHAR(20),
    salary NUMERIC(8,2) CHECK (salary > 0),
    FOREIGN KEY (dept_name) REFERENCES department
);
-- Multiple column primary key
CREATE TABLE takes (
    id CHAR(5),
    course_id CHAR(7),
    sec_id CHAR(3),
    semester VARCHAR(6),
    year NUMERIC(4,0),
    PRIMARY KEY (id, courseid, secid, semester, year)
);
-- Unique constraint
CREATE TABLE department (
    dept_name VARCHAR(20) UNIQUE,
    building VARCHAR(15),
    budget NUMERIC(12,2)
);

Referential Integrity

When foreign key constraint is violated, actions:

  1. Reject (default): Disallow operation
  2. Cascade: Propagate change
  3. Set NULL: Set foreign key to NULL
  4. Set DEFAULT: Set to default value
CREATE TABLE course (
    course_id CHAR(7) PRIMARY KEY,
    dept_name VARCHAR(20),
    FOREIGN KEY (dept_name) REFERENCES department
        ON DELETE CASCADE
        ON UPDATE CASCADE
);

Cascade Example:

  • Delete department → Automatically deletes all courses in that department
  • Update department name → Automatically updates dept_name in all courses

CHECK Constraints

-- Simple check
CREATE TABLE instructor (
    salary NUMERIC(8,2) CHECK (salary >= 0)
);
-- Complex check
CREATE TABLE section (
    semester VARCHAR(6),
    year NUMERIC(4,0),
    CHECK (semester IN ('Fall', 'Winter', 'Spring', 'Summer'))
);
-- Table-level check
CREATE TABLE time_slot (
    timeslotid CHAR(4),
    day VARCHAR(1),
    start_time TIME,
    end_time TIME,
    CHECK (starttime < endtime)
);

Assertions (Not Widely Supported)

Global constraints across tables:

-- Ensure every student has an advisor
CREATE ASSERTION studentadvisorcheck CHECK (
    NOT EXISTS (
        SELECT * FROM student
        WHERE totcred > 0 AND id NOT IN (SELECT studentid FROM advisor)
    )
);

Note: Few systems support assertions due to performance overhead.

SQL Data Types and Schemas

Built-in Types

  • BLOB: Binary Large Object (images, files)
  • CLOB: Character Large Object (documents)
  • XML: XML documents
  • JSON: JSON data (SQL:2023)

User-Defined Types

-- Distinct type (strong typing)
CREATE TYPE Dollars AS NUMERIC(12,2) FINAL;
CREATE TABLE department (
    dept_name VARCHAR(20),
    budget Dollars
);
-- Cannot mix types
-- budget + 100  -- ERROR
-- budget + CAST(100 AS Dollars)  -- OK

Domains

Create reusable constraints:

CREATE DOMAIN degree_level AS VARCHAR(10)
    CHECK (VALUE IN ('Bachelors', 'Masters', 'Doctorate'));
CREATE TABLE student (
    name VARCHAR(20),
    degree degree_level
);

Large Objects

-- Store images
CREATE TABLE images (
    image_id INT,
    image BLOB
);
-- Store documents
CREATE TABLE documents (
    doc_id INT,
    content CLOB
);

Indexes

Indexes dramatically speed up queries on specific attributes.

Creating Indexes

-- Single column index
CREATE INDEX instructornameidx ON instructor(name);
-- Multi-column index
CREATE INDEX takescourseidx ON takes(course_id, semester, year);
-- Unique index (enforces uniqueness)
CREATE UNIQUE INDEX studentididx ON student(id);

When to Use Indexes

Create indexes on:

  • Primary keys (usually automatic)
  • Foreign keys
  • Frequently queried columns
  • Columns in WHERE, ORDER BY, JOIN conditions

Don't overuse:

  • Indexes consume space
  • Slow down INSERT/UPDATE/DELETE

Dropping Indexes

DROP INDEX instructornameidx;

Example Impact

Without index: 

SELECT * FROM instructor WHERE id = '10101';
-- Scans all 100,000 records (slow)

With index: 

CREATE INDEX instructorididx ON instructor(id);
SELECT * FROM instructor WHERE id = '10101';
-- Direct lookup (fast)

Authorization

Control who can access/modify data.

Privileges

  • SELECT: Read data
  • INSERT: Add records
  • UPDATE: Modify records
  • DELETE: Remove records
  • ALL PRIVILEGES: All of the above

Granting Privileges

-- Grant SELECT to specific user
GRANT SELECT ON instructor TO user1;
-- Grant multiple privileges
GRANT SELECT, INSERT ON student TO user2;
-- Grant all privileges
GRANT ALL PRIVILEGES ON course TO admin;
-- Grant to all users
GRANT SELECT ON department TO PUBLIC;
-- Grant with ability to grant to others
GRANT SELECT ON instructor TO user3 WITH GRANT OPTION;

Revoking Privileges

-- Revoke SELECT
REVOKE SELECT ON instructor FROM user1;
-- Revoke with cascade
REVOKE SELECT ON instructor FROM user3 CASCADE;
-- Also revokes from anyone user3 granted to

Roles

Group users with similar privileges:

-- Create role
CREATE ROLE teaching_assistant;
-- Grant privileges to role
GRANT SELECT ON course TO teaching_assistant;
GRANT SELECT ON section TO teaching_assistant;
-- Assign role to users
GRANT teaching_assistant TO user4;
GRANT teaching_assistant TO user5;

Column-Level Authorization

-- Grant access only to specific columns
GRANT UPDATE (salary) ON instructor TO payroll_dept;
-- User can update salary but not other columns

Important Notes and Best Practices

Query Optimization

  1. Use EXISTS over IN for correlated subqueries (often faster)
  2. Use INNER JOIN explicitly rather than implicit joins in WHERE
  3. Create indexes on frequently queried columns
  4. Avoid SELECT * when you only need specific columns
  5. Use UNION ALL instead of UNION if duplicates are acceptable (faster)

Design Principles

  1. Minimize NULL values: Complicate queries and indexes
  2. Use foreign keys: Enforce referential integrity at database level
  3. Create views for complex queries used repeatedly
  4. Use transactions for multi-step operations requiring consistency
  5. Apply principle of least privilege: Grant minimum necessary access

Common Mistakes

  1. Forgetting NULL handling in outer joins
  2. Using natural join carelessly when attributes have same name but different meaning
  3. Not using indexes on large tables
  4. Over-indexing: Too many indexes slow down writes
  5. Granting excessive privileges: Security risk
